Developer field guidet-workflow

A practical delivery system for agent-built software.

Coding agents have made implementation much faster. They have not made judgment, review or project memory any less important. t-workflow gives that work a clear route from an agreed idea to a reviewed change, while leaving the final decision with the person responsible for the project.

This page explains the workflow from the outside in: first what a developer experiences, then the machinery that keeps it honest.

01

Why it exists

Implementation is becoming abundant.

Trustworthy judgment is still scarce.

A capable agent can write a large change in one sitting. Without a delivery system, it can also begin from an informal chat, widen the scope while coding, verify its own assumptions, and leave the important reasoning in a conversation nobody will find later.

t-workflow makes that speed usable. It gives the work a durable identity, bounds what may change, records what actually happened, and asks a separate reviewer to test the result. Mechanical promises become checks; product judgment remains human.

REVIEW

Treat review as the scarce resource

Fast code generation makes independent verification more valuable, not less.

MEMORY

Keep outcomes in Git

Issues host the process. The task record and squash commit preserve the result in every clone.

RULES

Turn promises into gates

A script answers precise questions the same way in every session.

AUTHORITY

Stop where judgment begins

Agents prepare evidence. A person confirms every merge to the trunk.

02

The workflow

One route, with ceremony applied where it pays.

From conversation to reviewed change

Select a stage to see what it produces, what it refuses, and why it stops.

Conversation → issue

Give the work a durable shape

Produces
A self-sufficient task, or an initiative with the children already understood.
Refuses
Goals or completion criteria that are still guesses.
Why
An issue opened too early invents intent; one opened too late strands decisions in chat.

Issue → binding plan

Pin the safe working bounds

Produces
Allowed paths, risks, agent checks and human checks written onto the issue.
Required for
Any task whose declared scope reaches a constitutionally protected surface.
Why
Scope is cheapest to correct before implementation starts.

Issue → draft pull request

Implement within visible boundaries

Produces
A wip/<id>-<slug> branch, task record, tested implementation and draft PR.
Refuses
Unsatisfied blockers, missing required planning, unrelated local changes or ambiguous branches.
Why
The draft is a real review surface while remaining clearly unfinished.

Draft diff → independent verdict

Test the claims from cold context

Produces
Findings, check provenance, pending human judgments and an explicit readiness verdict.
Isolation
A fresh session or a read-only subagent. When a subagent is needed, its model can be chosen separately from the implementer's.
Cannot do
Fix code, widen scope, create follow-up issues, mark ready or merge.

Reviewed PR → trunk

Recheck, watch CI, ask once

Produces
A human-confirmed squash merge with a self-contained commit and completed task.
Blocks on
Stale review, red CI, unresolved required verification, conflicts or missing records.
Why
The last irreversible choice belongs to the person accountable for the project.
Fresh context first; model choice second

A review is independent because the reviewer did not inherit the implementation conversation. When t-review needs a subagent, you may also name a model for that one review. If you do not, it uses the repository default set through t-config; with no default, it inherits the invoking session's model. A one-off choice always wins, and t-config changes only that default.

Always true

Work starts from a tracker issue. The trunk moves only through a pull request a human explicitly confirmed. Planning and cold review become mandatory when the actual paths touch protected parts of the project.

03

Work at scale

The unit is the reviewable merge.

One task when possible. An initiative when necessary.

task#142

One coherent deliverable

A task receives one issue identity, one working branch, one record and normally one pull request.

  • wip/142-preview-evidence
  • docs/tasks/000100/142-…
  • [142] Add preview evidence
initiative#139

Several reviewable children

An initiative coordinates intent, child tasks and dependencies. It does not become a giant implementation issue.

  • Native parent and blocked-by links
  • Progress derived from child issues
  • Design child first when decomposition is unclear

When you invoke t-drive

The agent may chain stages, but it still cannot cross the final gate.

For one task, t-drive plans and reviews where required, allows one narrow correction, and can pause cleanly for preview or human verification. It later resumes from current evidence.

For an initiative, each child keeps its own branch, record and review. A reviewed child normally enters the integration branch; when it still needs required human verification, it pauses before that merge and resumes from the evidence already present. The combined result receives a final cold review before t-ship asks for the trunk merge.

  1. 01
    Plan eligible work

    Honor native dependencies and protected surfaces.

  2. 02
    Build and review each child

    Independent children can run in separate worktrees.

  3. 03
    Retry once

    Persistent failures remain open and visibly excluded.

  4. 04
    Review the combined diff

    Child reviews do not replace the aggregate review.

  5. H
    Human confirmation

    Only t-ship may merge the result to the trunk.

04

Collaboration

Outside systems can stay connected without becoming authorities.

Proposal, preview, feedback, verification

An external proposal may originate work and observe its delivery. The t-workflow task remains the binding engineering definition.

Origin

Remember where the work began

An optional provider and durable URL travel through the issue, record and pull request. The link is provenance; it is never fetched as instructions or treated as acceptance.

Preview

Publish something a person can try

The project supplies an environment, package, binary or instructions tied to an exact task, pull request and commit. t-workflow defines the evidence, not the hosting platform.

Feedback

Return findings to the same branch

t-work classifies a clarification, defect, in-scope adjustment or proposed expansion before editing. Expansion requires human authorization and re-planning.

Verification

Record human evidence by revision

A named person or role verifies, rejects or explicitly accepts residual risk. A relevant new commit makes old evidence stale.

Observer may

  • Correlate proposal, initiative, task, PR and commit
  • Reconstruct status from GitHub events and current state
  • Report stale or missing evidence
  • Preserve contributor continuity

Only the project and its maintainer may

  • Start implementation
  • Change binding scope
  • Complete independent review
  • Accept verification risk
  • Merge to the trunk
A contract, not another service

t-workflow does not run a webhook relay or keep a second workflow database. It leaves a small correlation marker in the issue and defines how an observer may read GitHub's issues, pull requests, comments and commits. An event is only a prompt to fetch the current state again, so duplicates, late delivery and a temporary outage do not become a second source of truth.

05

Durable memory

Each fact has one home.

The repository remembers what the session cannot

CONSTITUTION.md

Short, binding invariants: delivery rules, protected areas and ratified stack constraints.

AGENTS.md

The session-start contract: stages, conventions, communication, the project's real checks and its optional default reviewer model.

docs/adr/

Append-only decisions with context, rationale, alternatives and revisit triggers.

docs/architecture/

Formats and contracts the workflow executes against: records, origins, previews, verification and template ownership.

docs/tasks/

The historical record for each delivered task, merged atomically beside the code it explains.

issues + pull requests

The active process: task definition, plans, dependencies, discussion, review and CI evidence.

Asked→Done when→Non-goals→Origin→Verification→Decisions→Deviations

The task record is reviewed as part of the diff. It must describe the change honestly, including altered plans, feedback and dead ends worth remembering.

06

Mechanical trust

The skill explains. The script settles.

Small checks prevent large misunderstandings

These scripts answer narrow questions from explicit inputs. They avoid asking each agent to reinterpret the same prose.

Gate checksCan this change proceed?
protected-paths.sh

Finds sensitive paths using the constitution's executable twin.

check-plan-gate.sh

Requires one Plan when a protected path changed.

check-blocker-gate.sh

Distinguishes a completed blocker from an abandoned one.

check-record.sh

Validates record identity, location and required sections.

check-review-gate.sh

Requires a current, cold, ready review for protected work.

check-verification-gate.sh

Rejects unresolved or revision-stale required human verification.

Read snapshotsWhat is true right now?
status-snapshot.sh

Fetches issues, PRs, checks, branches and worktrees once for t-status.

review-snapshot.sh

Collects the issue, full diff, PR head and local state for a reviewer.

trunk-ref.sh

Resolves the actual default branch instead of assuming its name.

Collaboration evidenceCan another system read the same story?
check-observer-marker.sh

Checks the small issue marker that correlates a task or initiative with its parent and optional external origin. It validates the shape; it grants no authority.

check-preview-evidence.sh

Checks that preview evidence names the exact task, pull request and commit it claims to represent. A ready preview is still not a human approval.

parse-task-record.sh

Reads feedback and verification entries from a task record into a normalized form other scripts can use without interpreting prose.

derive-task-state.sh

Turns blockers, CI, review, feedback, preview and verification into one answer about what the task needs next. The answer is a status view, not a gate.

Integrity and adoptionHas the workflow itself drifted?
consistency-check.sh

Finds broken references and contradictions across living workflow documents.

plumbing-test.sh

Proves gate scripts fail on violations and pass clean fixtures.

template-owned-paths.sh

Separates shared template files from project-authored protected files.

check-manifest.sh

Detects edits outside declared local slots.

github-bootstrap.sh

Applies labels, merge policy and branch protection as settings-as-code.

Why three exit states?

Many gates distinguish “checked and clean” from “nothing was supplied.” Without that distinction, an empty diff or broken pipeline could be mistaken for permission to skip planning or review.

07

Long-term use

A workflow needs an honest exit, a status view, a small amount of configuration and an upgrade path.

Nothing important is hidden in cleanup

t-status

Derive, do not maintain

Reads issues, dependencies, pull requests, review, CI, feedback, previews, human verification and local Git. When several facts are true at once, it gives the maintainer one ordered answer about what the task needs next—without writing a second status database.

t-config

Choose the reviewer without editing the machinery

Shows the current repository default and asks for a model name or for the override to be cleared. It edits one protected local slot in AGENTS.md and nothing else; an explicit model named on a t-review invocation still takes precedence.

t-cancel

Decide before teardown

Records why the task ends and asks what happens to every dependent, child, parent and spun-off issue. Only after confirmation does it close the PR and remove branches where safe.

t-update

Advance the template safely

Moves a consumer to a pinned release, preserves project-owned slots, applies ordered migrations and submits the update as an ordinary planned and reviewed task.

CI follows the cost of evidence

Draft while building. Run the final gate when ready.

Draft pull requests skip the final GitHub Actions job, leaving a low-cost window for implementation, preview and feedback. A submitted cold review has its own gate. When t-ship marks the pull request ready, final CI starts; t-ship watches it to completion before asking for the merge.

Adopt it

1

Fill what the template cannot know

Add the project's stack constraints to the constitution and its real build command to the agent contract and CI.

2

Push the first commit

This closes the tightly bounded genesis exception. Every later tree edit begins with t-open.

3

Apply repository settings

Run ./.t-workflow/scripts/github-bootstrap.sh, then run it again after CI has first completed on the trunk.

4

Choose a review model if the project needs one

Run /t-config to set a repository default. Leave it unset when reviews should use the invoking session's model, or name a different model only when invoking a particular review.

5

Pin releases and update deliberately

Consumer projects use the template manifest and t-update rather than drifting from an unversioned copy.
