Reference · GitHub Actions

Four workflows: gate every PR, and deploy this site.

Every job below is thin — it gathers the tracker/forge context a script needs (issue body, PR diff, review list) and hands it to one of the scripts on the Scripts page. The logic lives in the scripts, which is what lets plumbing-test.sh test it without a live GitHub Actions run.

ci.yml

Triggers: every PR (opened, synchronized, reopened, edited — so a title-only or issue-body-only edit gets a fresh run without a new commit) and every push to main.

JobRuns onEnforces
consistencyPR + push to main./.t-workflow/scripts/consistency-check.sh — the only job that also runs on plain pushes to main, not just PRs.
recordPR onlyA task PR carries its own docs/tasks/<bucket>/<id>-<slug>.md, verified with check-record.sh — or, on a driven initiative's wip/<id>-integration branch, one record per Task: #<id> line via check-record.sh --multi.
plan-gatePR onlyA protected diff carries exactly one ## Plan section, via check-plan-gate.sh — skipped (reported OK) on a driven initiative's integration branch, since each included child was already plan-gated individually before being merged in.
title-gatePR onlyThe PR title starts with [<id>] matching the branch, via check-title-gate.sh.
blockersPR onlyEvery blocker of the task's issue is closed as completed, via a live gh api graphql query (for stateReason, not yet in the tracker adapter's own contract table) piped into check-blocker-gate.sh.
plumbing-testPR only./.t-workflow/scripts/plumbing-test.sh — regression coverage for every gate script above, against fixtures.

A future project's own build/test command is added here as a third job once the stack exists — AGENTS.md §Checks item 1 is the one place that names it first.

review-gate.yml

Triggers: PR opened/synchronized/reopened, and pull_request_review submitted — split from ci.yml specifically because a new push invalidates the previous verdict, and a submitted review is what produces one to check in the first place.

Its one job, cold-review, fetches the PR's reviews and its head commit's timestamp, then hands both to check-review-gate.sh — confirming a protected PR carries a current, cold (not same session), readiness: ready review. This is the required status-check context named cold-review in branch protection; renaming the job means updating .t-workflow/scripts/github-bootstrap.sh in the same change.

installer.yml

Triggers: every PR, and every push to main.

Deliberately its own file rather than a job in ci.yml: every file in this repository is copied into the projects the installer generates, and a generated project has no installer/ directory at all — a job living in the shared ci.yml would be inherited by every generated project as a check pointing at a script that isn't there, red on that project's very first PR for a reason its owner couldn't diagnose. Its one job runs ./installer/test.sh against a full-history checkout (the test pushes HEAD into a throwaway repository and installs from that). Advisory only — github-bootstrap.sh doesn't name it as a required check, so it goes red on failure but doesn't block a merge on its own.

pages.yml

Triggers: push to main, or manually (workflow_dispatch).

Deploys this website. build checks out the repository and uploads site/ as a Pages artifact; deploy (depending on build) publishes it to GitHub Pages. Like installer.yml, it lives in its own file — stripped for every generated project along with the site/ directory it deploys, since that project has no template website to publish.

Every job name here is load-bearing. Each is a status-check context .t-workflow/scripts/github-bootstrap.sh marks required in branch protection (once it has actually run on main at least once) — renaming a job means updating that script in the same change, or branch protection silently stops enforcing it.
