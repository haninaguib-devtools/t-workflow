Reference · Installer

One command, one wholesale copy, one commit.

A project is created once. There is no separate "update an existing project" feature in the installer — a project generated today and a project generated a year from now both go through exactly this mechanism, and staying current afterward is a completely different command, /t-update (see the Migrations page). Do not confuse the two: this page is only about how a project first comes to exist.

Two files, split for a reason

installer/install.sh and installer/bootstrap.sh.

install.sh is the file people actually fetch — its path is a long-lived public contract:

curl -fsSL https://raw.githubusercontent.com/haninaguib-devtools/t-workflow/main/installer/install.sh | bash

Because that command pipes into bash, everything interactive has to live in the one file being fetched — so install.sh owns all of the argument parsing, --help, and every prompt. It reads answers from /dev/tty directly rather than stdin, since piping the script into bash already gave bash the stdin — a plain read there would consume the rest of the script, not the person's answer. Once every question has an answer (by flag or by prompt), it clones the template and hands off to bootstrap.sh, passing every resolved answer through environment variables (TWORKFLOW_SRC, TWORKFLOW_NAME, TWORKFLOW_TARGET, TWORKFLOW_REMOTE, TWORKFLOW_VISIBILITY, TWORKFLOW_SOURCE_URL). bootstrap.sh is never invoked directly by a person and never prompts — by the time it runs, every question already has an answer. Both scripts are bash-3.2 compatible, since macOS still ships that version.

What install.sh asks and does

  1. Parses flags: --name, --dir, --source, --ref (a branch or tag — never a raw commit id, since git clone can't fetch one and silently falling back to the default branch would record a version nobody asked for), --remote/--no-remote, --private/--public.
  2. Prompts for anything not given by flag — project name (validated against both filesystem and repository naming rules), and, if gh is installed and logged in, whether to create a GitHub repository now and at what visibility. With no terminal available, missing flags are a hard refusal rather than a hang.
  3. Clones the template at --ref into a throwaway temp directory (git clone --depth 1 --branch <ref>), refusing outright — no fallback to the default branch — if that exact ref can't be fetched.
  4. Confirms the clone actually looks like a t-workflow template (installer/bootstrap.sh exists in it), then hands off to it with every answer in the environment.

What bootstrap.sh does — the actual project creation

  1. Reads provenance before anything is deleted: the clone's short commit hash (git rev-parse --short HEAD) — needed for the README's "Generated from t-workflow @ <ref>" line, and unrecoverable once .git is gone.
  2. One wholesale copy: cp -R of the entire cloned tree into the target directory — not a file-by-file reconstruction, and not a templating engine. cp -R preserves a symlink as a symlink on both GNU and BSD, which is exactly what keeps CLAUDE.md, GEMINI.md, .github/copilot-instructions.md, and .agents/skills as aliases instead of separate, driftable copies.
  3. Strips what the template doesn't hand down: .git (a new project gets its own history), LICENSE, installer/, site/, .github/workflows/installer.yml, .github/workflows/pages.yml, and every subdirectory under docs/tasks/ except TEMPLATE.md and README.md (the template's own task history describes the template, not the new project).
  4. Writes a fresh README.md from installer/templates/README.md, substituting the project name, the template's commit ref, and — only when the source was an actual URL, not a local path used for testing — a browsable URL.
  5. Makes exactly one commit: git init with main as the default branch (via symbolic-ref, since git init -b main needs a newer git than every target has to support), then one commit whose message states the genesis exception explicitly — this commit happens outside the pipeline because there is no tracker and no main yet to open a PR against, and the exception ends the moment it's pushed. If git has no author identity configured, the script stops here rather than deleting the half-built tree — everything is built and only the commit is missing, so the person finishes it by hand with the exact commands the script prints.
  6. Optionally creates the GitHub repository (gh repo create ... --push) and, only on success, runs ./.t-workflow/scripts/github-bootstrap.sh from inside the new project to apply labels, squash-only merge settings, and branch protection. A failure here is never fatal — a local project with printed instructions for finishing by hand is a good outcome; a half-created remote is not.
  7. Prints what it could not do for you: the two fills no installer can know — CONSTITUTION.md §4 (stack constraints) and AGENTS.md §Checks item 1 (the build/test command) — plus, depending on whether a remote was actually pushed, either the exact by-hand commands to fold both fills into the still-open genesis commit, or the reminder that the genesis exception has already closed and both fills are now ordinary tasks through /t-open.

By hand, without the installer

Nothing above is mandatory machinery — README.md §Bootstrapping spells out the same seven steps done manually: copy the repo (or use it as a GitHub template) and git init; replace README.md from installer/templates/README.md before deleting it; delete LICENSE, installer/, site/, and the two template-only workflow files, then empty docs/tasks/ down to its template and README; make the two fills (plus CONSTITUTION.md §3 if application surfaces are already known); create the repository, commit, and push; run .t-workflow/scripts/github-bootstrap.sh. The installer is a convenience over exactly this sequence, not a different mechanism.

Not an update mechanism. Nothing above ever runs again against an existing project. Staying current with later template improvements is /t-update's job entirely — a separate command, run inside the generated project, that compares a pinned template version against a newer one and syncs only what changed. See the Migrations page.
