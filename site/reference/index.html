Introduction

In plain terms, before any internal vocabulary.

t-workflow is a set of instructions, checks, and file conventions that a coding agent (and a human) follow together so that changes to a codebase happen in a predictable, reviewable way. It is not an application framework — it has no opinion on your language, stack, or architecture. What it standardizes is the path a change takes: from a written-down request, through implementation, to a merge that a person explicitly approved.

Concretely, it is a folder of plain-language instructions (.claude/skills/), a short constitution of hard rules (CONSTITUTION.md), a handful of scripts that enforce the rules mechanically instead of relying on anyone remembering them, and a GitHub Actions setup that runs those scripts on every pull request. A tool called install.sh copies all of this into a brand-new repository in one command, and a later command, /t-update, keeps that copy current as the template itself improves.

The rest of this page gives the shape of the whole system. Each topic page listed above goes one level deeper into one part of it.

Overview

How a change moves from an idea to main, and the machinery that makes that safe to leave alone.

The pipeline, one command per stage

Every change — code, configuration, or documentation — starts the same way: a conversation converges into a written issue via /t-open. From there, a task moves through a small set of named stages, each a slash command: /t-plan pins down exactly which files may change and how the result will be checked; /t-work creates the branch, writes an implementation record, does the work, runs the checks, and opens a draft pull request; /t-review reads the finished diff with fresh eyes and posts findings; /t-ship is the only command that can merge, and it always stops to ask a human to confirm first. /t-cancel is the only way out that isn't a merge — it records why the work is being abandoned before anything is torn down. Two more commands round out the set: /t-drive, which chains planning, implementation, and review across every child of a larger initiative on one shared branch, stopping only once for a human's final confirmation; and /t-update, which brings a generated project's copy of the template current. /t-status gives a read-only snapshot of everything in flight. The full detail for each is on the Skills page.

Nothing chains on its own. Each command reports what it did and names the next command — a human decides whether and when to run it. The one deliberate exception is /t-drive, which is explicitly invoked to chain stages across many child tasks, but even it stops once, at the end, for a human to confirm the final merge.

Two rules that are never optional

Everything above is chosen per task except two things: work always starts from a tracker issue (never a silent edit to the tree), and main only ever moves by a pull request that a human explicitly confirmed. Those two rules carry almost all of the system's safety — every change has a durable, written statement of intent before any code exists, and nothing reaches the trunk unseen.

Protected surfaces get the full treatment

Some paths in the repository are considered load-bearing for the whole delivery system itself — the constitution, the skills, the CI configuration, the scripts, the architecture docs, and a handful of others. A change touching any of them always requires a plan before the work and an independent review before shipping, regardless of how small it looks. A script, .t-workflow/scripts/protected-paths.sh, is the executable, single source of truth for exactly which paths those are — the same list a human reads in prose in CONSTITUTION.md §3.

The tracker and the forge are pluggable

The instructions never say "GitHub" directly. Instead they call named operations like view an issue or open a pull request, and two small adapter documents — docs/adapters/TRACKER.md and docs/adapters/FORGE.md — map each one to a concrete command for whichever tool is actually in use (GitHub Issues and GitHub Pull Requests today). Adopting a different issue tracker or code host later means editing those two files, not rewriting every instruction.

A record travels with every change

Every task carries a short markdown file under docs/tasks/, created when work starts and merged in the same pull request as the change it describes. It captures what plain code cannot: what was asked, what was deliberately excluded, and any decisions or deviations made along the way. This is what lets a much later reader — human or agent — understand why a change happened, not just what it did.

How a project actually comes to exist

A new project is created once, by running the installer (installer/install.sh, handing off to installer/bootstrap.sh): it clones this template repository, copies the whole tree into a new directory, strips out everything that only makes sense for the template itself (the installer, this website, the license), writes a fresh README.md, and makes one commit. There is no per-file templating step beyond that — it is a plain, wholesale copy. See the Installer page for the full mechanism.

That is not the end of the relationship, though: a generated project can later pull in improvements made to the template itself, via /t-update, which compares the project's currently-pinned template version against a newer one, applies any file changes and any necessary migrations, and lands the whole thing as one ordinary reviewed task. See the Migrations page for exactly how that works.
