Reference · Scripts

Eleven scripts. Rules the build enforces, not rules to remember.

Every script under scripts/ is a pure function over explicit inputs — files, stdin, or arguments — so each one is testable against fixtures without ever calling the tracker or the forge live. scripts/plumbing-test.sh is exactly that fixture suite, and it runs on every PR.

The protected-surface list, executable

protected-paths.sh

CONSTITUTION.md §3's protected-path list, in machine-checkable form — the single source three skills (/t-work, /t-review, /t-ship), /t-status, and CI all read, so no one of them can quietly drift from what the constitution says. Matches paths against an ordered glob list (CONSTITUTION.md, AGENTS.md, .claude/*, docs/adr/*, scripts/*, installer/*, and more) using bash pattern matching, and un-quotes a git-style quoted non-ASCII path first so one can't slip through unprotected.

Usage: protected-paths.sh <path>... (exit 0 if any is protected, 1 if none), --stdin (one path per line — the form every caller with a real diff should prefer), or --list (print the raw patterns). Exit 2 means nothing was even checked — a broken caller, never treated as "clean."

Called by: /t-work, /t-review, /t-ship, /t-status, /t-drive, /t-update, plus check-plan-gate.sh and check-review-gate.sh below, plus consistency-check.sh itself (checking the script and CONSTITUTION.md §3 agree, both directions).

Cross-document consistency

consistency-check.sh

The mechanized half of keeping the governance documents from drifting apart. Runs ten checks over every "living document" (AGENTS.md, CONSTITUTION.md, README.md, docs/*.md, every ADR, architecture doc, and adapter, the task-record template/README, and every SKILL.md) — deliberately excluding historical task records, which describe the tree as it was, not as it is.

  • §-references (§3) resolve to a real heading in a document the line actually names.
  • ADR-NNN pointers resolve to a real file, and a decision reference (ADR-001 §D4) resolves to a real ### D4. heading in it.
  • Named-section references (AGENTS.md §Checks) resolve to a real heading.
  • The AGENTS.md pipeline table and .claude/skills/ agree, in both directions — a table row with no skill directory, or a skill directory with no table row, both fail.
  • Retired vocabulary (lane names, ADR-001's superseded no-issue fix path) doesn't reappear in living guidance.
  • No skill cites a docs/workflow.md section — skills are self-contained by design.
  • Every tracker:*/forge:* operation a skill names is actually defined in an adapter.
  • protected-paths.sh and CONSTITUTION.md §3 name the same surfaces, both directions — the reverse direction (a surface named in prose but not enforced) is the load-bearing one.
  • Every code fence opens and closes cleanly (a stray same-line closer leaves a block open, silently rendering the rest of a document as code).

Usage: ./scripts/consistency-check.sh [root]. Exit 0 = clean; non-zero = every violation listed on stdout.

Called by: every skill's standing check set (AGENTS.md §Checks item 2); the consistency job in ci.yml, on every PR and every push to main.

The task-record and PR-shape gates

check-record.sh

Verifies a task record's identity lines and template shape against the task id its branch names — the record-honesty rule, mechanized. Confirms the heading reads <id> — <Title>, an Issue: #<id> line is present, and every ## section docs/tasks/TEMPLATE.md defines appears — read from the template itself, never hardcoded, so it can't silently drift from it.

Usage: check-record.sh <id> <record-file> [template-file] for an ordinary task; check-record.sh --multi <pr-body-file> [template-file] (changed paths on stdin) for a driven initiative's aggregate PR, which locates and checks one record per Task: #<id> line in the PR body.

Called by: the record job in ci.yml.

check-plan-gate.sh

Mechanizes the plan-before-protected-work rule: given the diff's changed paths and the issue body, confirms a protected diff carries exactly one ## Plan section — missing or duplicated both fail.

Usage: changed paths on stdin, check-plan-gate.sh <issue-body-file>. Exit 0 on an unprotected diff, or a protected one with exactly one plan; 1 otherwise; 2 if nothing was checked.

Called by: the plan-gate job in ci.yml.

check-title-gate.sh

Confirms a PR's title starts with [<id>], matching the id parsed from its wip/<id>-<slug> branch — the narrowest possible check, deliberately: /t-ship's own squash-subject convention is free to differ once merged.

Usage: check-title-gate.sh <id> <pr-title>.

Called by: the title-gate job in ci.yml.

check-blocker-gate.sh

Confirms every blocker of a task's issue is closed as completed — a blocker closed as not-planned (cancelled via /t-cancel) was abandoned, not satisfied, and still fails this.

Usage: check-blocker-gate.sh <blockers-json-file>, a JSON array of {number, state, stateReason} — the shape gh api graphql's blockedBy field returns.

Called by: the blockers job in ci.yml.

check-review-gate.sh

Mechanizes /t-ship's review precondition: on a protected diff, the latest review must read readiness: ready, its isolation: line must not be same session, and it must be newer than the head commit (a later commit means the review is about a different diff).

Usage: changed paths on stdin, check-review-gate.sh <head-commit-iso8601> <reviews-json-file>.

Called by: the cold-review job in review-gate.yml.

The update manifest

check-manifest.sh

The one implementation of the manifest's normalized-hash rule, and the CI lock a consuming project wires in. Strips everything strictly between a <!-- local -->/<!-- /local --> marker pair before hashing, so a consumer's own local-slot content never registers as drift; a symlink is hashed by its target, never its resolved content.

Usage: check-manifest.sh --hash-file <path> prints one file's normalized sha256 (what /t-update writes into the manifest); with no arguments (or --manifest <path>), verifies every file .template-manifest.json lists against the working tree. In this template repo itself it's a deliberate no-op — there is no manifest here, since this repo is the template, not a pinned consumer.

Called by: /t-update (writing and later re-verifying); a consumer's own CI, as a required check this repo doesn't run on itself.

template-owned-paths.sh

Computes the manifest's file list: every tracked file matching a protected pattern, minus the paths that are genesis-only — stamped once at bootstrap (README.md) or deleted outright for every generated project (LICENSE, installer/*, site/*, the installer and pages workflows). It is itself template-owned, so a future change to what counts as template-owned reaches consumers the normal way.

Usage: template-owned-paths.sh --list.

Called by: /t-update, run against the scratch clone of the target tag to get that tag's own view of the file list.

Repository setup and regression coverage

github-bootstrap.sh

Settings as code: creates the workflow's labels (initiative, cancelled, and the four classification labels), sets squash-only merge mechanics with delete-branch-on-merge, and applies branch protection on main — PRs only, no force pushes, zero required approvals on purpose (GitHub forbids approving your own PR, so requiring one in the solo phase would make every PR unmergeable by its only author). Marks CI's job names as required status checks only once they've actually run on main at least once, since GitHub rejects a context it has never seen.

Usage: run once after creating the GitHub repository, from a checkout with gh logged in. Idempotent — safe to re-run, which is exactly how it picks up the required-checks step the first run couldn't do yet.

Called by: installer/bootstrap.sh, when a remote was created; a person, by hand, otherwise (and again once CI has run on main).

plumbing-test.sh

Regression coverage for the plumbing behind every gate above: protected-paths.sh's exit codes and non-ASCII quoting, the ID-bucket math (<bucket> = id rounded down to the nearest 100), and every check-*.sh script against both a passing and a failing fixture. Entirely fixture-based — nothing here calls the tracker or the forge, so it runs identically locally and in CI.

Usage: ./scripts/plumbing-test.sh, from anywhere (paths resolve from the script's own location).

Called by: the plumbing-test job in ci.yml, on every PR.
