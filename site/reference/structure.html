Reference · Project structure

Every file the installer places, and what it's for.

This is the whole tree a new project starts with, minus the template-only parts the installer strips out at generation time (noted below). Several entries link to a deeper page — this one is the map.

Governance, at the root

The files every agent reads before touching anything.

PathWhat it is
CONSTITUTION.mdThe project's invariants: delivery rules, the decision log's own rules, the protected-surface list (§3), and a reserved §4 for the consuming project's own stack/architecture constraints. Binding on every task; changes only by PR at the heightened approval bar.
AGENTS.mdWhat an agent reads on session start: the pipeline table, the tracker-write and scope conventions, the communication rules, and the one place the project's build/test check is named (§Checks). The session-start contract.
CLAUDE.md, GEMINI.md, .github/copilot-instructions.mdFilesystem symlinks to AGENTS.md — not separate copies. They exist only so Claude Code, Gemini CLI, and GitHub Copilot each find the instructions at the filename they expect. Edit only AGENTS.md; the aliases can never drift.
.agents/skillsA symlink to .claude/skills/, so a tool that looks for skills in the agent-neutral location finds the same files. Edit only .claude/skills/.
README.mdPer-project, not template content beyond the version the installer writes from installer/templates/README.md at genesis (project name and provenance filled in). A protected surface once genesis closes.
.gitignoreOS/editor noise, local secrets, and .claude/settings.local.json (per-machine agent settings that must never be committed).
LICENSEMIT, naming the template's copyright holder — stripped from every generated project. A generated project ships with none; its own licence is the project owner's choice.

.claude/ — the executable instructions

The whole directory is a protected surface, not only skills/.

.claude/skills/<name>/SKILL.md holds one file per stage — t-open, t-plan, t-work, t-review, t-drive, t-ship, t-cancel, t-update, t-status — nine directories today. Full detail on each is the Skills page. A generated project may also carry .claude/agents/ (subagent definitions) or .claude/settings.json (hooks and permission allowlists) if the project adds them; neither exists in this template repo itself, but both are covered by the same protected-surface rule the moment they do, since either changes what an agent does when it runs.

docs/ — the durable record

Everything here is meant to survive losing the tracker and forge. Full tour on the docs/ tour page.

PathWhat it is
docs/workflow.mdThe cross-stage shape of the pipeline — what spans stages, not what any one stage does. The skills are self-contained and never cite it for their own instructions.
docs/adr/One append-only file per architecture decision, numbered. Ships with ADR-001 (the baseline) through the latest; a consuming project's own decisions start at the next number.
docs/adapters/TRACKER.md, docs/adapters/FORGE.mdThe backend maps: every tracker:* and forge:* operation a skill names, mapped to a concrete command (GitHub by default). Swapping either backend means editing these two files only.
docs/architecture/Binding conventions the skills execute against: confirmation gates, issue-template design, local-content slots, the update manifest, and the migrations convention.
docs/tasks/TEMPLATE.md, docs/tasks/README.mdThe shape of every future task record, and the bucketing convention (<bucket>/<id>-<slug>.md). Protected; the individual records under docs/tasks/<bucket>/ are not.
Task records are emptied at generation time. The template's own history under docs/tasks/<bucket>/ describes this repository, not the one being generated — installer/bootstrap.sh deletes every record subdirectory, keeping only TEMPLATE.md and README.md.

.t-workflow/scripts/ and .github/ — mechanical enforcement

Rules the build enforces beat rules a model must remember.

.t-workflow/scripts/ holds eleven shell scripts — the executable form of the constitution's protected-path list, the CI gates it feeds, and their own regression tests. .github/workflows/ runs most of them on every pull request, plus deploys this website. Both get their own deep-dive pages: Scripts and GitHub Actions. .github/ISSUE_TEMPLATE/ (task.yml, initiative.yml, config.yml) gives a hand-opened issue the same shape /t-open produces — see docs/ tour for the design spec.

migrations/

Empty on a fresh project, and empty in this template too — until the first breaking change needs one.

Holds one append-only V<n>__<slug>.md file per breaking template change; ships with only a README.md landing pad so the directory exists in git before any migration does. See the Migrations page for the full shape and how /t-update applies one.

What a generated project does not get

Stripped by installer/bootstrap.sh at generation time — present in this template repo, absent everywhere it produces.

  • .git — a new project gets its own history, not a fork of the template's.
  • LICENSE — see above.
  • installer/ — a project doesn't ship the tool that made it.
  • site/ — this website describes the template, not the project being generated.
  • .github/workflows/installer.yml and .github/workflows/pages.yml — the installer's own test, and this site's deploy workflow; each lives in its own file precisely so removing it is one deletion, never text surgery on a shared, protected CI file.

Full detail on exactly how and when these are stripped is on the Installer page.
