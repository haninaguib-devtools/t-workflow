Reference · Migrations

Staying current, on purpose, on request.

A project is generated from the template exactly once (see the Installer page). Everything on this page is about what happens afterward: how a generated project can later pull in template improvements without losing its own local content, via one command, /t-update.

Releases are tags; a consumer pins one

The template's own releases are ordinary git tags on main — v1, v2, and so on — cut by hand after a sync-point PR merges. A generated project always pins one exact tag; it never tracks main or "latest." That pinned tag is the unit /t-update moves between.

The manifest: .template-manifest.json

Committed at a consumer project's root once it has synced at least once (first adoption has none yet). It records the template repository, the currently-pinned tag, the highest migration number already applied, and — for every template-owned file — a normalized sha256 hash.

templateThe template repo, owner/name. First adoption reads this from the consumer's own README.md provenance line if no manifest and no explicit source exist yet.
tagThe template release this project is currently synced to.
migrations_appliedThe highest migration number already applied; /t-update applies only what's greater than this.
filesEvery template-owned path at that tag, mapped to its normalized hash at that tag — the exact set the CI lock enforces. Nothing outside it is ever touched by a sync.

Which files count as template-owned is not simply every protected path: scripts/template-owned-paths.sh --list is the executable answer — every protected, tracked file minus the ones that are genesis-only (stamped once, like README.md, or deleted outright for every generated project, like LICENSE or site/) — there is nothing in a consumer repo for those to sync to.

Normalized hashing, and local slots

A template-owned file may carry one or more <!-- local --> … <!-- /local --> regions — exactly two exist today, CONSTITUTION.md §4 (stack/architecture constraints) and AGENTS.md §Checks item 1 (the build/test command) — bracketing content that is the consumer's own by design. Before hashing, everything strictly between a marker pair is stripped (the markers themselves stay), so a consumer's own slot edits never register as drift. A file with no markers hashes as-is; a symlink (CLAUDE.md, .agents/skills, …) is hashed by its target, never its resolved content, since one of them points at a directory. scripts/check-manifest.sh --hash-file <path> is the single implementation of this rule — both writing the manifest and later verifying it call the same function, so the two can never compute a hash two different ways.

The CI lock

scripts/check-manifest.sh, run with no arguments, reads the manifest, recomputes every listed file's normalized hash from the working tree, and fails — listing every path that drifted or went missing — the moment any of them no longer matches. A consuming project wires this into its own CI as a required check; this template repo does not run it on itself, since it carries no manifest and the result would only ever say "no manifest," which is expected, not a failure.

Breaking changes: migrations/

Most template updates are a plain file sync — copy the new version over the old one, re-apply local slots. A migration exists only when that isn't enough: something about the change needs the consumer's own state touched — a renamed operation a consumer's scripts might call, a moved section a cross-reference points at, a file that no longer exists.

One append-only file per breaking change lives in migrations/, named V<n>__<slug>.md with a strictly increasing <n> (gaps allowed, renumbering never). Each file states what broke, gives the upgrading agent concrete, followable steps (not prose a human has to interpret), and a Done-when check the agent can run immediately after applying it.

/t-update reads every migration file in the target tag greater than the manifest's current migrations_applied, applies them strictly in increasing order, checks each one's own Done-when immediately after — stopping the whole update, unresolved, the moment one fails — then writes the new highest applied number back into the manifest.

How /t-update puts it all together

  1. Reads the current pin (or falls back to the README's provenance line on first adoption) and fetches the target tag into a scratch clone outside this repo's own working tree — nothing here is touched yet.
  2. Refuses outright if any currently-owned file has drifted from what the manifest recorded — a hand-edit outside its local slot since the last sync means the manifest can no longer be trusted, and the fix is upstreaming that edit first, never silently overwriting it here.
  3. Computes, read-only, exactly what would change: the new file list, which files are added/changed/unchanged, and which migrations would apply.
  4. Gates on the human's confirmation — current tag → target tag, file counts, migrations that would apply — before writing or calling the tracker at all.
  5. Only on confirmation does it open its own task: an issue, a branch, and a record — the first file this skill writes inside the repo happens only after the task branch exists.
  6. Applies the sync: a plain copy for files with no local-slot markers; for CONSTITUTION.md and AGENTS.md, splices the target tag's file whole but keeps this repo's current content inside every local-slot region; applies pending migrations in order.
  7. Writes the new manifest, then runs /t-work Phase 3 verbatim — checks (including check-manifest.sh against what was just written), commit, push, draft PR.

A sync almost always touches a protected surface — template-owned files are protected surfaces by construction — so it gets the same plan-and-review treatment any other protected change does. There is no fast path, by design.

Not the installer, run again. /t-update never re-runs anything in installer/ — a generated project has no installer/ directory at all (it was stripped at genesis). This is a wholly separate mechanism, purpose-built for a project that already exists. See the Installer page for how a project is created the one time that happens.
