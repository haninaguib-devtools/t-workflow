Reference · docs/ tour

What lives under docs/, and why it's there.

docs/workflow.md aside (the cross-stage shape — covered on the Overview page), docs/ has four subdirectories: decisions, backend adapters, binding architecture conventions, and task records. Everything here is meant to survive losing the tracker and the forge entirely — it lives in git, in every clone.

docs/adr/ — the decision log

One append-only file per decision, numbered, never edited after acceptance — only superseded by a later one.

ADRDecides
001The Phase 0 baseline: two invariants (issue-first, human-confirmed-PR-only main), everything else chosen per task except protected surfaces; the (later superseded) no-issue fix path; cancellation's five safety rules; the 100-ID record-bucket scheme; one home per fact; enumeration never silently truncates.
002Trims the baseline after a week of real use: drops the optional worktree stage and the no-issue fix path entirely, replaces ship/cancel's automatic teardown with (at the time) a deferred /t-clean skill, and drops the non-numeric tracker-key clause.
003Replaces body-text Part of:/Blocked-by: markers with GitHub's native sub-issues and issue dependencies, keeping Split from: as body text (no native equivalent exists) and the initiative label (native fields give progress, not identity).
004Introduces /t-drive: one integration branch per driven initiative, a bounded one-retry-then-exclude self-correction policy, and generalizing the squash-commit convention to one Task: #<id> line per included child.
005Retires /t-clean itself (ADR-002's own replacement, now judged unused by the same standing-cost test ADR-002 applied to what it removed): a stale local worktree or branch is left alone permanently, cleaned up by hand only if it's ever actually in the way.

Each carries its own context, decision, rationale, alternatives considered, and revisit triggers in full — this table is a map, not a substitute for reading one.

docs/adapters/ — pluggable backends

The reason no skill instruction ever names "GitHub" directly.

TRACKER.md and FORGE.md each declare an active-backend (GitHub for both, today) and map every named operation a skill calls — tracker:view, tracker:create, forge:pr-merge, and so on — to one concrete command for that backend. TRACKER.md also carries the four classification labels (bug, enhancement, documentation, question) and the workflow-reserved labels (initiative, cancelled) that stay outside a human's own labeling vocabulary. Several relation operations (set-parent, add-blocker, and the fields they read) need gh ≥ 2.94.0 — an older client rejects them outright rather than degrading quietly. Adopting a different tracker or forge means editing these two files only; every skill instruction is unchanged.

docs/architecture/ — binding conventions

Not decisions with alternatives-considered rationale (that's what ADRs are for) — settled conventions the skills execute against.

confirmation-gates.md

The single home for how every human-confirmation gate behaves, so /t-ship, /t-cancel, and /t-update all ask the same way: evidence first in plain language, exactly one question, the accepted answers named explicitly, and never proceeding on silence.

issue-templates.md

The design spec for .github/ISSUE_TEMPLATE/'s GitHub issue forms (task.yml, initiative.yml, config.yml), which mirror /t-open's own body shape so a hand-opened issue arrives with the same structure — chosen as forms, not plain markdown templates, specifically so a missing Goal or Done-when is refused at submission time rather than silently omitted.

local-slots.md

Fixes the vocabulary for the two places a template-owned file is per-repo by design: CONSTITUTION.md §4 and AGENTS.md §Checks item 1, each wrapped in its own <!-- local --> … <!-- /local --> pair. Also documents the symlink-alias mechanism (CLAUDE.md, GEMINI.md, .github/copilot-instructions.md → AGENTS.md; .agents/skills → .claude/skills/).

manifest.md

The update-manifest format and the normalized-hashing rule that lets a consuming project's own local-slot edits pass a sync without ever registering as drift. Full detail on the Migrations page.

migrations.md

The convention for a breaking template change: when a migration file is actually needed (a plain sync isn't enough), its exact shape, and how /t-update applies one. Full detail on the Migrations page.

docs/tasks/ — the record shape

One markdown file per task, created on its branch and merged atomically with the change it describes.

TEMPLATE.md fixes the shape every record follows: Asked, Done when, Explicitly not, Decisions made along the way, and Deviations / notes — read by .t-workflow/scripts/check-record.sh directly from the template file itself, never hardcoded, so the check can't silently drift from the shape it's supposed to verify. README.md states the bucketing convention: a record lives at docs/tasks/<bucket>/<id>-<slug>.md, where <bucket> is the task's tracker-issue id rounded down to the nearest 100 and zero-padded to six digits — task 142 lands in docs/tasks/000100/. Both files are protected; the individual records they shape are not.

A record is what lets a much later reader understand why a change happened, not only what it did — and, being part of the diff, it's reviewed too: does it honestly describe this change, decisions and deviations included?
