A practical workflow for shipping software with coding agents.

t-workflow gives every change a clear path from request to pull request. It keeps scope, decisions, checks, and human approval visible without tying your project to a language or framework.

What it is

A small delivery system that lives in your repository.

It is a set of plain-language instructions, checks, and task records that coding agents can follow consistently. Your application stack stays yours.

01

Work starts with a clear issue

The goal, completion criteria, scope, exclusions, and blockers are written down before implementation begins.

02

Context ships with the change

Every task pull request includes a record of what was asked, what changed, and which decisions were made along the way.

03

A human controls every merge

Agents prepare the implementation and evidence. main moves only through a pull request that a person explicitly confirms.

The workflow

Five stages on the main task path

Each command does one job, reports what happened, names the next command, and stops.

  1. 1/t-open

    Open the work

    Turns the request into one task issue, an initiative with child tasks, or a design task when the shape is not yet clear.

    ProducesIssue
  2. 2/t-plan

    Pin the boundaries

    Records the allowed files, known risks, and separate agent and human checks. Required for protected paths.

    ProducesPlan
  3. 3/t-work

    Implement the task

    Creates the task branch and record, works inside scope, runs the checks, and opens a draft pull request.

    ProducesDraft PR
  4. 4/t-review

    Review in cold context

    Checks the full diff against the issue, plan, record, and repository rules, then posts findings and readiness.

    ProducesReview
  5. 5/t-ship

    Confirm and merge

    Shows the final evidence, asks the human for confirmation, and squash-merges with a self-contained commit.

    ProducesTrusted main

Skill reference

Ten focused commands cover the full lifecycle.

The five core commands move a task forward. Five supporting commands handle driving an initiative, cancellation, cleanup, template sync, and status.

/t-openCore

Open work

Create the correctly shaped tracker issue from a settled request. No branch or code is created yet.

/t-planCore

Plan a task

Add binding allowed paths, risks, constraints, and validation ownership to an existing issue.

/t-workCore

Implement a task

Check the gates, create or resume the task branch, write the record, implement, verify, and open a draft PR.

/t-reviewCore

Review a pull request

Independently inspect the task in cold context and post prioritized findings with an explicit readiness verdict.

/t-driveOptional

Drive an initiative

Walk an initiative's children to completion on one integration branch — plan, implement, and independently review each — then stop once for a single confirmed pull request to main.

/t-shipCore

Ship a task

Check the PR and review evidence, obtain human confirmation, then squash-merge and close the task.

/t-cancelTerminal

Cancel a task

Record why the work stopped, decide the effect on related issues, and clean up the PR, branch, and worktree.

/t-cleanOptional

Clean up a stale worktree

Remove a shipped or cancelled task's stale local worktree and branch, lazily, and only on confirmation.

/t-updateOptional

Sync template updates

For a repo generated from this template: sync its template-owned files to a pinned release, preserving local slots and applying pending migrations.

/t-statusRead only

Show pipeline status

Summarize open initiatives and tasks, blockers, pull requests, CI, reviews, and useful warnings without changing anything.

Built-in rules

The important parts are difficult to skip.

Issue before implementation. A fresh session can understand the task without access to the original conversation.

Records live in git. Outcomes and durable decisions travel with every clone of the repository.

Protected paths get more scrutiny. Plans and independent reviews are required where mistakes cost more.

No automatic stage chaining. Each stage stops so the next decision remains visible.

Human-confirmed pull requests. Every change to main ends at a clear human merge gate.
